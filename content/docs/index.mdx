A centered Dialog is unusable under a thumb. The shadcn docs answer with a
recipe: combine Dialog and Drawer yourself behind a `useMediaQuery` hook.
Every team rewrites that boilerplate, and usually badly — casted types,
clobbered `className`s, lost callbacks, duplicated children. **responsivecn**
ships the canonical, installable version of that recipe, following the shadcn
conventions: open code, install from a registry, compound components.

A **pair** is a curated desktop→mobile combination. Each pair produces a
**responsive component**: a drop-in replacement for the desktop component that
renders the mobile one below the breakpoint. Four pairs exist:

| Pair              | Responsive component               |
| ----------------- | ---------------------------------- |
| Dialog → Drawer   | [`DialogDrawer`](/docs/dialog-drawer) |
| Sheet → Drawer    | `SheetDrawer`                      |
| Popover → Drawer  | `PopoverDrawer`                    |
| Tooltip → Popover | `TooltipPopover`                   |

Each pair exists on both bases of the ecosystem: the bare slug is the Base UI
item (the shadcn default base), and the `-radix` suffix is the Radix variant.

## Installation

```bash
npx shadcn@latest add @responsivecn/dialog-drawer
```

On a Radix project, install the `-radix` item instead:

```bash
npx shadcn@latest add @responsivecn/dialog-drawer-radix
```

<Callout title="Namespace resolution">

Until the `@responsivecn` namespace resolves globally in the shadcn CLI, the
full URL form works everywhere:

```bash
npx shadcn@latest add https://responsivecn.com/r/dialog-drawer.json
```

</Callout>

The install pulls the official shadcn items the component builds on
(`dialog`, `drawer`, `use-mobile`, …) as registry dependencies — you get the
standard building blocks, not copies of them.

## The override prop

A responsive component takes the desktop component's props 1:1, on the root
and on every part — migrating means changing your imports, nothing else.
Mobile behaviour is tuned through the **override prop**, named after the
mobile side of the pair: `drawer={{...}}` on `DialogDrawer`, `SheetDrawer` and
`PopoverDrawer`; `popover={{...}}` on `TooltipPopover`. It exists on the root
**and on every part**, and is typed 1:1 on the mobile counterpart's API — no
casts.

```tsx
<DialogDrawer drawer={{ snapPoints: [0.5, 1] }}>
  <DialogDrawerTrigger className="w-full">Open</DialogDrawerTrigger>
  <DialogDrawerContent
    className="sm:max-w-lg"
    drawer={{ className: "max-h-[80dvh]" }}
  >
    …
  </DialogDrawerContent>
</DialogDrawer>
```

The merge rules are identical for all four pairs — only the prop name changes:

- **`className` merges** — `cn(shared, mobile)`: the shared class still
  applies below the breakpoint, the mobile one wins on conflicts.
- **State callbacks compose** — for the root's state callbacks (`onOpenChange`,
  `onOpenChangeComplete`), the shared handler runs first, then the mobile one.
- **Every other prop replaces** the shared value below the breakpoint.

Outside the override prop, each side keeps its native defaults: an explicit
shared prop is forwarded to both sides, and nothing is auto-mapped between the
two APIs — a drawer opens from the bottom by default, regardless of how the
desktop side is placed.

## How it works

The **breakpoint** is fixed at 768px, read through the standard shadcn
`use-mobile` hook — the same one the shadcn Sidebar uses. At 768px and up the
desktop component renders; below, the mobile one. This is a conditional
render, not CSS: only one side is mounted at a time.

<Callout type="warn" title="State loss when crossing the breakpoint">

Crossing 768px unmounts one side and mounts the other. Everything inside the
overlay loses its internal state — uncontrolled form fields included. State
held outside the component (a controlled `open`, lifted form values) survives.
Design forms accordingly: lift anything you cannot afford to lose.

</Callout>
